## 2. دليل التثبيت والإعداد

### الخطوة 1 — تنزيل المشروع

```bash
git clone https://github.com/helfaramawi/real_estate_tax_project.git
cd real_estate_tax_project
git checkout claude/real-estate-tax-backend-ua7ex
```

### الخطوة 2 — تشغيل قاعدة البيانات والخدمات الأساسية

```bash
# تشغيل جميع الخدمات (قاعدة البيانات + API + Redis + ML + MLflow)
docker compose -f docker-compose.yml -f docker-compose.intelligence.yml up -d
```

انتظر حتى تكتمل جميع الخدمات (حوالي 2-3 دقائق). تحقق من الحالة:

```bash
docker compose ps
```

يجب أن تكون جميع الحاويات في حالة **healthy** أو **running**.

### الخطوة 3 — تطبيق مخطط قاعدة بيانات الذكاء الاصطناعي

```bash
# نسخ ملف الترحيل إلى الحاوية
docker cp src/RealEstateTax.Infrastructure/Migrations/V2__Intelligence_Schema.sql retax_postgres:/tmp/V2.sql

# تطبيق المخطط
docker exec retax_postgres psql -U retax_user -d retax_db -f /tmp/V2.sql
```

يجب أن ترى رسائل مثل `CREATE TABLE`, `CREATE INDEX`, `ALTER TABLE`.

### الخطوة 4 — التحقق من تشغيل النظام

افتح في المتصفح:
- **الواجهة الرئيسية**: `http://localhost:8080`
- **توثيق API (Swagger)**: `http://localhost:8080/swagger`
- **لوحة الوظائف الخلفية**: `http://localhost:8080/hangfire`
- **لوحة نماذج الذكاء الاصطناعي**: `http://localhost:5001`

### الخطوة 5 — تشغيل الواجهة الأمامية (للتطوير)

```bash
cd frontend
npm install
npm run dev
```

افتح المتصفح على: `http://localhost:3001`

## 3. التهيئة والضبط

### ملف إعدادات API الرئيسي

الملف: `src/RealEstateTax.API/appsettings.json`

#### إعدادات قاعدة البيانات

```json
"ConnectionStrings": {
  "DefaultConnection": "Host=postgres;Port=5432;Database=retax_db;Username=retax_user;Password=YOUR_PASSWORD"
}
```

#### إعدادات JWT (المصادقة)

```json
"Jwt": {
  "Secret": "YOUR_SECRET_KEY_MIN_32_CHARACTERS",
  "Issuer": "RealEstateTaxPlatform",
  "Audience": "RealEstateTaxPlatform",
  "ExpiryMinutes": "60"
}
```

> **تحذير أمني**: غيِّر `Secret` إلى قيمة عشوائية طويلة في بيئة الإنتاج.

#### إعدادات خدمة الذكاء الاصطناعي

```json
"MLService": {
  "BaseUrl": "http://ml_service:8001",
  "InternalSecret": "dev-secret"
}
```

> في الإنتاج: غيِّر `InternalSecret` إلى قيمة سرية قوية.

#### مفاتيح الميزات (Feature Flags)

```json
"FeatureManagement": {
  "GpsCapture": true,
  "OfflineSync": true,
  "GeoFencing": true,
  "RouteOptimization": false,
  "MLRiskScoring": false,
  "FraudDetection": false,
  "DuplicateDetection": false,
  "ValuationPrediction": false,
  "UnregisteredBuildingDetection": false,
  "GeoClusteringDashboard": false
}
```

**شرح كل مفتاح:**

| المفتاح | الوصف | متى تفعّله؟ |
|---------|-------|-------------|
| `GpsCapture` | تسجيل مسارات GPS للمفتشين | فوراً |
| `OfflineSync` | مزامنة البيانات دون اتصال | فوراً |
| `GeoFencing` | مناطق المراقبة الجغرافية | فوراً |
| `RouteOptimization` | تحسين مسارات التفتيش | بعد تجهيز البيانات |
| `MLRiskScoring` | نموذج تقييم المخاطر | بعد تدريب النموذج |
| `FraudDetection` | كشف الاحتيال | بعد تدريب النموذج |
| `DuplicateDetection` | كشف التكرارات | بعد تدريب النموذج |
| `ValuationPrediction` | التنبؤ بالقيمة | بعد تدريب النموذج |
| `UnregisteredBuildingDetection` | كشف المباني غير المسجلة | بعد تدريب النموذج |
| `GeoClusteringDashboard` | لوحة التجمعات الجغرافية | بعد تجهيز البيانات |

**لتفعيل ميزة:** غيِّر `false` إلى `true` ثم أعد تشغيل API:
```bash
docker compose restart api
```

## 4. دليل المستخدم — الوظائف الأساسية

### تسجيل الدخول

1. افتح `http://localhost:8080` أو `http://localhost:3001`
2. أدخل اسم المستخدم وكلمة المرور
3. انقر **دخول**

**بيانات الدخول الافتراضية:**

| اسم المستخدم | كلمة المرور | الدور |
|------------|------------|------|
| superadmin | SuperAdmin@123! | مدير النظام |
| admin | Admin@123! | مسؤول |
| assessor1 | Assessor@123! | محاسب |
| inspector1 | Inspector@123! | مفتش |
| collector1 | Collector@123! | محصل |

### لوحة التحكم الرئيسية

تعرض لوحة التحكم:
- **إجمالي العقارات**: عدد العقارات المسجلة
- **إجمالي الفواتير**: فواتير الضريبة الصادرة
- **المدفوعات المعلقة**: الفواتير التي لم تُسدَّد
- **الموافقات المعلقة**: العمليات التي تنتظر المراجعة

### إدارة العقارات

**مسار:** القائمة الجانبية → العقارات

**العمليات المتاحة:**
- **عرض قائمة العقارات** مع إمكانية البحث والتصفية
- **إضافة عقار جديد**: اسم، نوع، موقع، مساحة، سنة البناء
- **تعديل بيانات عقار** موجود
- **ربط الموقع الجغرافي** بإحداثيات GPS
- **رفع مستندات** الملكية

### فواتير الضريبة

**مسار:** القائمة الجانبية → فواتير الضريبة

**دورة حياة الفاتورة:**
```
مسودة ← صادرة ← مدفوعة
                ← متأخرة ← معلقة
```

**إصدار فاتورة:**
1. انقر **فاتورة جديدة**
2. اختر العقار والمكلف
3. أدخل المبلغ وتاريخ الاستحقاق
4. انقر **إصدار**

### المدفوعات

**مسار:** القائمة الجانبية → المدفوعات

تسجيل دفعة جديدة:
1. ابحث عن الفاتورة
2. انقر **تسجيل دفعة**
3. أدخل المبلغ وطريقة الدفع
4. احفظ — تُحدَّث حالة الفاتورة تلقائياً

### التقييمات

**مسار:** القائمة الجانبية → التقييمات

عملية التقييم تتبع **مبدأ الصانع-المدقق** (Maker-Checker):
1. **المحاسب** يُنشئ التقييم ويدخل القيمة السوقية
2. **المراجع** يراجع ويعتمد أو يرفض
3. **المدير** يُقرِّر في حالة الاختلاف

### المعاينات الميدانية

**مسار:** القائمة الجانبية → المعاينات الميدانية

**إنشاء معاينة:**
1. اختر العقار
2. حدد المفتش المسؤول
3. أدخل تاريخ المعاينة
4. المفتش يُرفق صور وإحداثيات GPS من الموقع

### الطعون

**مسار:** القائمة الجانبية → الطعون

**مراحل الطعن:**
```
مقدَّم ← قيد المراجعة ← مُحال للجنة ← مُحسوم
```

## 5. الذكاء الاصطناعي والتحليل الجغرافي

**مسار:** القائمة الجانبية → الذكاء الاصطناعي

### 5.1 خريطة المخاطر (Heatmap)

تعرض هذه الخريطة **كثافة المخاطر الضريبية** لكل منطقة جغرافية.

**كيفية القراءة:**

| اللون | معنى درجة الخطر |
|-------|----------------|
| 🔴 أحمر | خطر مرتفع جداً (≥ 75%) |
| 🟠 برتقالي | خطر مرتفع (50% - 74%) |
| 🟡 أصفر | خطر متوسط (25% - 49%) |
| 🟢 أخضر | خطر منخفض (< 25%) |

**كيفية الاستخدام:**
1. افتح تبويب **خريطة المخاطر**
2. تكبير على المنطقة المطلوبة
3. حرِّك المؤشر فوق أي دائرة لرؤية:
   - متوسط درجة الخطر بالنسبة المئوية
   - عدد العقارات في هذه المنطقة
4. إذا كنت تستخدم شاشة لمس أو لم يظهر التلميح عند التحويم، انقر على الدائرة لفتح بطاقة التفاصيل أسفل الخريطة.
5. استخدم هذه المعلومات لتحديد أولويات التفتيش

### 5.2 الشذوذات (Anomalies)

تعرض العقارات التي تظهر عليها **سلوكيات غير طبيعية** يكشفها الذكاء الاصطناعي.

**أنواع الشذوذات:**

| النوع | الوصف |
|------|-------|
| مبنى غير مسجل | مبنى موجود فعلياً لكن غير مسجل رسمياً |
| قيمة شاذة | القيمة المُعلنة مختلفة جداً عن السوق |
| ملكية مشبوهة | تغييرات ملكية مريبة أو متكررة |
| تداخل في الحدود | تقاطع حدود العقار مع عقارات أخرى |
| إحداثيات مكررة | عدة عقارات على نفس الموقع الجغرافي تماماً |
| عقار وهمي | بيانات غير منطقية أو متضاربة |
| تعارض في المعاينة | نتائج المعاينة تتناقض مع السجلات |

**درجات الخطورة:**

| الدرجة | الإجراء المطلوب |
|-------|----------------|
| 🔴 حرج (Critical) | تدخل فوري خلال 24 ساعة |
| 🟠 مرتفع (High) | مراجعة خلال أسبوع |
| 🟡 متوسط (Medium) | مراجعة خلال شهر |
| 🟢 منخفض (Low) | مراجعة دورية |

**التعامل مع الشذوذات:**
1. انقر على أي نقطة في الخريطة لفتح تفاصيل الشذوذ
2. اقرأ الوصف والأدلة
3. اختر الإجراء المناسب:
   - **قيد التحقيق**: ابدأ التحقيق وأحِل للمفتش
   - **تم الحل**: سُوِّيت المشكلة
   - **غير صحيح**: الإنذار كان خاطئاً (false positive)

### 5.3 التجمعات الجغرافية (Clusters)

تُجمِّع هذه الخريطة العقارات المتقاربة ذات الخصائص المتشابهة.

**فائدة التجمعات:**
- تحديد المناطق ذات القيم المرتفعة أو المنخفضة
- اكتشاف التفاوتات في التقييم داخل نفس المنطقة
- تخطيط جولات التفتيش بكفاءة

**قراءة الفقاعات:**
- **حجم الفقاعة**: عدد العقارات في التجمع
- **النص عند التحريك**: اسم المحافظة، عدد العقارات، متوسط القيمة بالمتر المربع

### 5.4 مراجعة التنبؤات

**مسار:** القائمة الجانبية → مراجعة التنبؤات

هذه الصفحة تعرض **نتائج نماذج الذكاء الاصطناعي** لكل عقار.

**أنواع التنبؤات:**

| النوع | ما يقيسه |
|------|---------|
| RiskScore | احتمالية المخالفة الضريبية (0-100%) |
| FraudProbability | احتمالية الاحتيال |
| DuplicateDetection | احتمالية التكرار مع عقار آخر |
| ValuationAnomaly | شذوذ في القيمة المُعلنة |
| CollectionProbability | احتمالية التحصيل الناجح |

**التصفية والبحث:**
- اختر نوع التنبؤ من القائمة المنسدلة
- اضبط **الحد الأدنى للدرجة** لتصفية النتائج
- مثال: `MLRiskScoring` + درجة `>= 75%` يعرض العقارات عالية الخطر فقط

**تفسير SHAP (شرح القرار):**
عند النقر على أي تنبؤ، تظهر لوحة **تفسير القرار** التي توضح:
- الأعمدة **الحمراء**: عوامل **رفعت** درجة الخطر
- الأعمدة **الخضراء**: عوامل **خفّضت** درجة الخطر
- طول العمود = قوة تأثير هذا العامل

مثال على القراءة:
```
DaysSinceLastSurvey  ████████ +0.23  ← لم تُفتَّش منذ فترة طويلة (خطر أعلى)
OverdueCount         █████    +0.15  ← فواتير متأخرة (خطر أعلى)
PaidOnTimeRate       ████     -0.12  ← معدل دفع جيد (يخفف الخطر)
```

**إجراءات المراجعة:**

| الإجراء | المعنى |
|---------|--------|
| ✅ تأكيد | النموذج صحيح، ابدأ الإجراء |
| ❌ رفض | النموذج مخطئ (false positive) |
| ⬆ تصعيد | أحِل للمستوى الأعلى |

> **ملاحظة**: قرارات المراجعة تُغذِّي بيانات التدريب المستقبلية وتحسِّن دقة النموذج.

## 6. تدريب نماذج الذكاء الاصطناعي

### 6.1 فهم المنظومة

تعمل منظومة الذكاء الاصطناعي على **ثلاث طبقات**:

```
┌─────────────────────────────────────────────┐
│         قاعدة البيانات (PostgreSQL)          │
│  بيانات العقارات + الفواتير + المعاينات     │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│         مخزن الميزات (Feature Store)         │
│   intel.feature_vectors                      │
│   35 متغير لكل عقار (موقع، قيمة، تاريخ...)  │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│      خدمة ML (Python FastAPI + XGBoost)      │
│   نموذج تقييم المخاطر + كشف الاحتيال        │
└─────────────────────────────────────────────┘
```

### 6.2 الخطوة الأولى — حساب الميزات

**ماذا يحدث؟**
يقرأ النظام كل عقار ويحسب 35 متغيراً يصف حالته:

| الفئة | المتغيرات |
|------|----------|
| الموقع الجغرافي | خط العرض، خط الطول، وجود حدود مرسومة |
| خصائص العقار | المساحة، النوع، سنة البناء، الطوابق، الوحدات |
| التقييم المالي | القيمة الإيجارية، القيمة السوقية، معدل الرسملة |
| تاريخ الدفع | عدد الفواتير، معدل الدفع في الوقت، الفواتير المتأخرة |
| المعاينات | عدد المعاينات، الأيام منذ آخر معاينة، دقة GPS |
| سجل المخاطر | درجة الخطر السابقة، عدد بلاغات الاحتيال |
| الملكية | طول سلسلة الملكية، أيام منذ آخر نقل، هل المالك شركة |

**كيفية التشغيل:**

**الطريقة 1 — من لوحة Hangfire (الأسهل):**
1. افتح `http://localhost:8080/hangfire`
2. انقر **Recurring Jobs** في شريط التنقل
3. ابحث عن `feature-computation-daily`
4. انقر **Trigger now**
5. راقب التقدم في **Jobs → Succeeded**

**الطريقة 2 — من سطر الأوامر:**
```bash
curl -X POST http://localhost:8080/api/v2/intelligence/batch-inference \
  -H "Authorization: Bearer YOUR_JWT_TOKEN" \
  -H "Content-Type: application/json"
```

**الطريقة 3 — تشغيل تلقائي يومي:**
الوظيفة تعمل تلقائياً كل يوم الساعة 2 صباحاً (مُضبطة مسبقاً في Hangfire).

**متابعة التقدم:**
```bash
docker logs retax_api -f | grep "Feature computation"
```

يجب أن ترى رسائل مثل:
```
Feature computation job started, version=v1
Processing 1500 properties in 3 batches
Batch 1/3 complete
Batch 2/3 complete
Batch 3/3 complete
Feature computation job complete for 1500 properties
```

**التحقق من النتائج في قاعدة البيانات:**
```bash
docker exec retax_postgres psql -U retax_user -d retax_db \
  -c "SELECT COUNT(*), feature_version FROM intel.feature_vectors GROUP BY feature_version;"
```

### 6.3 الخطوة الثانية — تدريب نموذج تقييم المخاطر

**المتطلبات:** يجب أن يكون مخزن الميزات ممتلئاً (الخطوة 6.2).

**تشغيل التدريب:**
```bash
curl -X POST http://localhost:8001/train/start \
  -H "X-Internal-Secret: dev-secret" \
  -H "Content-Type: application/json" \
  -d '{
    "model_name": "risk_scorer",
    "feature_version": "v1",
    "params": {
      "n_estimators": 200,
      "max_depth": 6,
      "learning_rate": 0.1
    }
  }'
```

**ماذا يحدث أثناء التدريب؟**
1. تُقرأ البيانات من جدول `intel.feature_vectors`
2. تُقسَّم إلى 80% تدريب / 20% اختبار
3. يُدرَّب نموذج **XGBoost** مع **5 طيات تحقق متقاطع**
4. تُحسب مقاييس الأداء (AUC, Precision, Recall, F1)
5. تُحسب قيم **SHAP** لشرح قرارات النموذج
6. يُحفظ النموذج في `/app/models/risk_scorer_production.pkl`
7. تُسجَّل التجربة في **MLflow**

**وقت التدريب المتوقع:**

| حجم البيانات | الوقت التقريبي |
|------------|--------------|
| < 10,000 عقار | 2-5 دقائق |
| 10,000 - 100,000 | 15-30 دقيقة |
| > 100,000 | 1-3 ساعات |

## 10. دليل الشاشات التفصيلي وسير العمل التشغيلي

> هذا القسم يشرح الشاشات كما يراها المستخدم النهائي، وما الذي يحدث خلف كل إجراء، وما هي قواعد العمل والصلاحيات المرتبطة به. استخدمه كدليل تدريب للمستخدمين وكمرجع للمراجعين قبل التشغيل الفعلي.

### 10.1 شاشة تسجيل الدخول والأمان

**الغرض:** دخول المستخدم إلى النظام حسب الدور المصرح به.

**مكونات الشاشة:**
```
┌────────────────────────────────────────────┐
│ شعار ريتاكس                                │
│ اسم المستخدم: [________________]           │
│ كلمة المرور: [________________]            │
│ [تسجيل الدخول]                             │
│ تنبيه: لا تشارك كلمة المرور مع أي شخص      │
└────────────────────────────────────────────┘
```

**سير العمل:**
1. يدخل المستخدم اسم المستخدم وكلمة المرور.
2. يتحقق النظام من الحساب، حالة التفعيل، وكلمة المرور.
3. عند النجاح يصدر النظام رمز JWT ويعرض الواجهة حسب الدور.
4. عند الفشل تظهر رسالة عامة بدون كشف تفاصيل أمنية.

**قواعد العمل:**
- لا يسمح بدخول الحسابات غير النشطة.
- يجب تغيير كلمة المرور الافتراضية في أول تشغيل إنتاجي.
- كل طلب محمي بعد تسجيل الدخول يحتاج رمز JWT صالح.
- انتهاء الجلسة يتطلب إعادة تسجيل الدخول أو تجديد الرمز حسب إعدادات النظام.

**الصلاحيات:** كل الأدوار تستطيع تسجيل الدخول إذا كان الحساب نشطاً.

---

### 10.2 شاشة لوحة التحكم الرئيسية

**الغرض:** إعطاء ملخص سريع عن حالة التحصيل والتشغيل.

**مكونات الشاشة:**
```
┌──────────────┬──────────────┬──────────────┬──────────────┐
│ عدد العقارات │ فواتير صادرة │ مدفوعات معلقة│ موافقات معلقة│
└──────────────┴──────────────┴──────────────┴──────────────┘
┌────────────────────────────┐ ┌────────────────────────────┐
│ مؤشرات التحصيل             │ │ تنبيهات المخاطر             │
└────────────────────────────┘ └────────────────────────────┘
```

**ماذا يرى المستخدم؟**
- إجمالي العقارات المسجلة.
- عدد الفواتير الصادرة والمتأخرة.
- المدفوعات الجديدة أو غير المطابقة.
- معاملات تحتاج اعتماد أو مراجعة.
- تنبيهات المخاطر والشذوذات الجغرافية.

**قواعد العمل:**
- المؤشرات المعروضة تعتمد على صلاحية المستخدم.
- المفتش يرى ما يتعلق بالمعاينات والتكليفات.
- المحصل يرى الفواتير والتحصيلات فقط.
- المدير يرى مؤشرات عامة وإجمالية.

---

### 10.3 شاشة إدارة العقارات

**الغرض:** إنشاء وتحديث ومراجعة سجل العقار.

**مكونات الشاشة:**
```
┌────────────────────────────────────────────────────────┐
│ بحث: [عنوان / كود / مالك]  نوع العقار: [فلتر]          │
│ [إضافة عقار] [تصدير]                                   │
├────────┬──────────────┬────────────┬─────────┬────────┤
│ الكود  │ العنوان       │ الحالة     │ المالك  │ إجراءات│
└────────┴──────────────┴────────────┴─────────┴────────┘
```

**الحقول المهمة عند إضافة عقار:**
- العنوان التفصيلي.
- المحافظة/المدينة/الحي.
- نوع العقار.
- المساحة.
- سنة البناء.
- الإحداثيات الجغرافية أو حدود العقار.
- مستندات الملكية أو الحيازة.

**سير العمل:**
1. إنشاء العقار بحالة `Draft`.
2. استكمال البيانات والمستندات.
3. إرسال للمراجعة.
4. التحقق من البيانات وربط المالك.
5. اعتماد العقار كـ `Verified` ثم تحديد هل هو خاضع للضريبة أو معفى.

**قواعد العمل:**
- لا ينتقل العقار إلى حالة خاضع للضريبة قبل اكتمال بيانات الملكية والتقييم.
- لا يجوز حذف عقار عليه فواتير أو مدفوعات إلا وفق سياسة الأرشفة/الحذف الناعم.
- أي تغيير حساس في العقار يجب أن يظهر في سجل التدقيق.
- الإحداثيات الجغرافية مطلوبة للوظائف المكانية والتحليل الذكي.

**الصلاحيات:**
- `SuperAdmin/Admin`: كل العمليات.
- `TaxOfficer/Assessor`: إنشاء وتحديث ومراجعة بيانات ضريبية.
- `FieldInspector`: تحديث بيانات المعاينة والحقول الميدانية فقط.
- `Collector`: قراءة محدودة مرتبطة بالفواتير والتحصيل.

---

### 10.4 شاشة المكلفين والملّاك

**الغرض:** إدارة بيانات الأشخاص والشركات المالكة أو المكلفة بالضريبة.

**مكونات الشاشة:**
```
┌────────────────────────────────────────────────────────┐
│ بحث: [اسم / رقم قومي / سجل تجاري]  [إضافة مكلف]        │
├────────────┬────────────┬─────────────┬───────────────┤
│ الاسم       │ النوع       │ رقم الهوية   │ عدد العقارات   │
└────────────┴────────────┴─────────────┴───────────────┘
```

**قواعد العمل:**
- الرقم القومي المصري 14 رقماً للأفراد.
- الشركات تستخدم رقم تسجيل/سجل تجاري حسب التهيئة القانونية.
- مجموع نسب الملكية على العقار يجب أن يصل إلى 100% قبل الاعتماد النهائي.
- لا يجوز تكرار نفس المكلف بنفس رقم الهوية إلا بقرار دمج/تصحيح.

**سير العمل:**
1. إنشاء ملف مكلف.
2. ربط المكلف بعقار أو أكثر.
3. تحديد نسبة الملكية.
4. مراجعة التعارضات أو التكرارات.
5. اعتماد العلاقة بين المكلف والعقار.

---

### 10.5 شاشة التقييم والربط الضريبي

**الغرض:** حساب القيمة وربط الضريبة بعد اعتماد البيانات.

**مكونات الشاشة:**
```
┌────────────────────────────────────────────┐
│ العقار: [اختيار]                           │
│ طريقة التقييم: [إيجارية/سوقية/تكلفة]       │
│ القيمة المقترحة: [________]                │
│ ملاحظات المقيم: [____________________]     │
│ [حفظ كمسودة] [إرسال للاعتماد]              │
└────────────────────────────────────────────┘
```

**قواعد العمل:**
- لا يصدر تقييم نهائي بدون اعتماد مراجع مخول.
- قواعد الضريبة والنسب يجب أن تكون قابلة للتحديث وليست ثابتة داخل الكود.
- يجب حفظ سبب الاعتماد أو الرفض.
- في حالة وجود طعن قائم، قد يتم تعليق أثر التقييم حسب السياسة القانونية.

**سير العمل Maker-Checker:**
1. `Assessor/TaxOfficer` ينشئ التقييم.
2. `Reviewer/Admin` يراجع المستندات والقيمة.
3. إذا تم الرفض يعود التقييم للتعديل.
4. إذا تم الاعتماد يصبح التقييم مصدراً للربط والفوترة.

---

### 10.6 شاشة الفواتير والتحصيل

**الغرض:** إصدار فواتير الضريبة ومتابعة حالتها.

**دورة حياة الفاتورة التفصيلية:**
```
مسودة → صادرة → مدفوعة جزئياً → مدفوعة بالكامل
          │            │
          │            └→ متأخرة إذا تجاوزت تاريخ الاستحقاق
          └→ ملغاة بصلاحية مدير فقط
```

**قواعد العمل:**
- لا تصدر فاتورة بدون تقييم/ربط معتمد.
- المدفوعات الجزئية تخفض الرصيد ولا تغلق الفاتورة إلا عند اكتمال السداد.
- المدفوعات الزائدة تحتاج مراجعة أو تسوية.
- إلغاء الفاتورة يحتاج سبباً وصلاحية إدارية.

**الصلاحيات:**
- `TaxOfficer/Admin/SuperAdmin`: إصدار وتعديل حالات الفواتير المصرح بها.
- `Collector`: تسجيل المدفوعات ومراجعة أرصدة الفواتير.
- باقي الأدوار: قراءة حسب الحاجة التشغيلية.

---

### 10.7 شاشة المدفوعات والتسويات

**الغرض:** تسجيل التحصيل وتحديث أرصدة الفواتير.

**مكونات الشاشة:**
```
┌────────────────────────────────────────────┐
│ رقم الفاتورة: [بحث]                        │
│ المبلغ المدفوع: [________]                 │
│ طريقة الدفع: [نقدي/بنك/إلكتروني/محفظة]     │
│ مرجع الدفع: [________]                     │
│ [تسجيل الدفع]                              │
└────────────────────────────────────────────┘
```

**قواعد العمل:**
- لا يقبل النظام مبلغاً سالباً أو صفراً.
- يجب وجود مرجع دفع للمدفوعات البنكية/الإلكترونية.
- يمنع تكرار نفس مرجع الدفع لنفس الفاتورة إلا بتسوية مصرح بها.
- كل دفع ناجح يحدث حالة الفاتورة تلقائياً.

---

### 10.8 شاشة الطعون والاعتراضات

**الغرض:** إدارة اعتراض المكلف على التقييم أو الربط أو الفاتورة.

**سير العمل:**
```
مقدم → قيد المراجعة → جلسة/لجنة → قرار → مغلق
```

**قواعد العمل:**
- يجب تسجيل تاريخ تقديم الطعن وسبب الاعتراض.
- أي مستندات داعمة ترفع مع الطلب.
- المدة القانونية للطعن يجب تأكيدها في سجل القرارات القانونية قبل الإنتاج.
- قرار اللجنة يجب أن يحدث الأثر المالي إذا كان مقبولاً.

**الشاشات الفرعية:**
- بيانات الطعن.
- المستندات.
- مواعيد الجلسات.
- قرار اللجنة.
- الأثر على الفاتورة/التقييم.

---

### 10.9 شاشة الإعفاءات

**الغرض:** تسجيل وتطبيق الإعفاءات القانونية أو المؤقتة.

**قواعد العمل:**
- كل إعفاء يحتاج نوعاً قانونياً ومرجعاً أو مادة قانونية.
- بعض الإعفاءات تكون مرتبطة بفترة زمنية.
- لا يطبق الإعفاء على الفواتير إلا بعد الاعتماد.
- يجب حفظ أثر الإعفاء على الرصيد أو القيمة الخاضعة للضريبة.

**الصلاحيات:**
- `Admin/SuperAdmin/TaxOfficer`: إنشاء ومراجعة الإعفاء حسب السياسة.
- `Compliance/Legal` أو المراجع القانوني: مراجعة المرجعية القانونية عند الحاجة.

---

### 10.10 شاشة المعاينات الميدانية

**الغرض:** تكليف المفتشين وجمع بيانات ميدانية موثقة.

**سير العمل:**
```
مكلف → قيد التنفيذ → مقدم → معتمد/مرفوض
```

**قواعد العمل:**
- كل معاينة يجب أن ترتبط بعقار ومفتش.
- صور الموقع وإحداثيات GPS مطلوبة للمعاينات الحساسة.
- لا يعتمد تقرير ميداني ناقص البيانات.
- رفض التقرير يجب أن يتضمن سبباً واضحاً لإعادة المعاينة.

**الصلاحيات:**
- `FieldInspector`: تنفيذ ورفع التقرير.
- `Admin/Reviewer`: اعتماد أو رفض التقرير.
- `TaxOfficer`: الاطلاع على النتائج وربطها بالتقييم.

---

### 10.11 شاشة المخاطر والذكاء التشغيلي

**الغرض:** تحديد الأولويات بناءً على المخاطر والشذوذات.

**قواعد العمل:**
- نتائج الذكاء الاصطناعي لا تكون قراراً نهائياً وحدها.
- كل تنبيه عالي الخطورة يحتاج مراجعة بشرية.
- تأكيد أو رفض التنبؤات يحسن النماذج لاحقاً.
- لا تستخدم النماذج في الإنتاج إلا بعد اعتماد المقاييس وتسجيل النموذج.

**الشاشات:**
- خريطة المخاطر.
- قائمة الشذوذات.
- مراجعة التنبؤات.
- تفسير SHAP أو أسباب القرار.

## 12. ملخص قواعد العمل الحرجة قبل الإنتاج

1. لا اعتماد نهائي لأي عقار بدون بيانات ملكية مكتملة.
2. مجموع نسب الملكية يجب أن يساوي 100% قبل الاعتماد.
3. لا تصدر فاتورة بدون تقييم/ربط معتمد.
4. لا تغلق الفاتورة إلا عند اكتمال السداد أو التسوية المعتمدة.
5. المدفوعات الزائدة أو المكررة تحتاج تسوية ومراجعة.
6. الطعون والإعفاءات يجب أن تحمل مرجعاً قانونياً أو قراراً موثقاً.
7. نتائج الذكاء الاصطناعي مساعدة للقرار وليست بديلاً عن المراجعة البشرية.
8. كل إجراء حساس يجب أن يترك أثراً في سجل التدقيق.
9. كل تغيير في قواعد الضريبة يجب أن يكون قابلاً للتتبع بتاريخ نفاذ واعتماد.
10. لا يتم إغلاق المشروع إنتاجياً دون أدلة CI وTRX وقرار اعتماد نهائي.

## 13. سيناريو تشغيل كامل من البداية للنهاية

### الحالة: تسجيل عقار جديد حتى تحصيل أول فاتورة

1. **الموظف الضريبي** ينشئ عقاراً جديداً ويدخل العنوان والمساحة والبيانات الأساسية.
2. يربط النظام العقار بالمكلف أو المالك ويطلب استكمال نسب الملكية.
3. يتم إرسال العقار للمراجعة والتحقق من المستندات والموقع الجغرافي.
4. **المفتش الميداني** ينفذ معاينة ويرفع الصور والإحداثيات.
5. **المقيم/الموظف الضريبي** ينشئ تقييم العقار بناءً على البيانات المعتمدة.
6. **المراجع أو المدير** يعتمد التقييم أو يرفضه مع سبب.
7. بعد الاعتماد، يصدر النظام فاتورة ضريبية.
8. **المحصل** يسجل الدفع عند السداد.
9. يحدث النظام حالة الفاتورة تلقائياً إلى مدفوعة جزئياً أو بالكامل.
10. تظهر العملية في لوحة التحكم والتقارير وسجل التدقيق.

### نقاط الرقابة في السيناريو
- التحقق من اكتمال البيانات قبل الاعتماد.
- فصل الصانع عن المدقق في التقييم.
- عدم السماح للمحصل بتعديل التقييم أو العقار.
- تسجيل كل تغيير حساس في سجل التدقيق.
- إمكانية فتح طعن أو إعفاء حسب السياسة القانونية.
